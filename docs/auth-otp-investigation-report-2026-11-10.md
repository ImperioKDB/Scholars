# Scholars Auth OTP Investigation Report

**Date:** 10 November 2026  
**Project:** Scholars  
**Production domain:** `https://www.scholars.com.ng`

## Problems under investigation

This investigation covered four related symptoms:

1. New-account confirmation emails were not consistently reaching the recipient inbox.
2. The signup screen displayed confirmation-link language instead of a usable OTP entry flow.
3. Password-reset emails were initially delivered as dead links and later displayed an eight-digit token even though the product copy said “six-digit code.”
4. The frontend reported invalid and expired verification failures with the same message.

## Evidence

The supplied Supabase Auth export showed successful Auth API responses for signup, resend, and recovery requests. It did not include the rendered email body or a provider-level inbox-delivery result. One exported signup event was classified as `user_repeated_signup`, which means that test did not represent a clean first-time registration for that address.

The supplied Gmail screenshot shows a current reset email containing the visible token `07139785`. That is an **eight-digit** token. The email was accepted and recorded by Brevo, but the earlier confirmation-email test did not appear in the recipient inbox. Brevo acceptance proves that the message reached Brevo’s sending pipeline; it does not prove Gmail accepted, classified, or displayed the message in the inbox.

The deployed application source before this fix had `OTP_LENGTH = 6` in the shared OTP component. It therefore could not submit the eight-digit token generated by the production Supabase Auth configuration. The source also contained a generic verification message: “That code is invalid or has expired.”

## Root causes identified

### 1. Provider and frontend token-length mismatch

Supabase’s current production Auth configuration is generating eight-digit email OTPs. The frontend was hard-coded to six input boxes and only attempted verification after six digits. This made the delivered reset token impossible to enter correctly.

Supabase documents `{{ .Token }}` as the email OTP variable and describes the OTP as six digits in its general documentation, but Supabase also exposes an Email OTP length setting in the Email provider configuration. The production screenshot is direct evidence that this project is currently set to eight digits.

### 2. Earlier link-style templates were incompatible with the OTP flow

The original templates used `{{ .Token }}` as an `href` destination. That is incorrect: `{{ .Token }}` is a numeric OTP, not a URL. A link such as `<a href="{{ .Token }}">` cannot be used by the OTP frontend.

The reset screenshot now shows the corrected visible-token format. Confirmation delivery still needs a clean new-account test using the saved confirmation template and a recipient address that has not previously existed in Supabase Auth.

### 3. Brevo acceptance and inbox placement are different stages

For the reset email, Brevo recorded the message and Gmail displayed it, so the reset path has demonstrated provider acceptance and inbox receipt.

For the confirmation email, Brevo recording a send without the message appearing in the inbox indicates that the message passed into Brevo’s sending pipeline, but the export does not prove final inbox placement. The remaining possibilities include recipient-side spam/quarantine, provider suppression or bounce history, a Gmail thread/conversation view hiding the newest message, or a confirmation-template/send path that differs from the reset path. SMTP credentials alone cannot distinguish these outcomes.

## Changes applied

The repository was updated to:

- Render eight OTP input boxes in the shared signup and recovery component, matching the live Supabase setting.
- Describe the delivered token as an eight-digit code.
- Keep paste and automatic verification limited to exactly eight digits.
- Return a distinct expired-code message when Supabase returns an expiry-specific error code.
- Return a distinct invalid-code message for other verification failures.
- Preserve the existing signup, login-rescue, recovery, resend, Google OAuth, and legacy-link compatibility flows.

The changes are in commit `12c0d4ed8f5f6dd3d8e3dc1f2e00cf980dd60181` and will be deployed through the connected GitHub-to-Vercel pipeline after validation.

## Required decision for the final product behavior

There are two valid configurations, but the provider and frontend must use the same length:

### Option A — Keep the current production setting

Keep Supabase Email OTP length at eight and use the newly deployed eight-digit frontend. This matches the token shown in the supplied Gmail screenshot.

### Option B — Use six digits as the original product requirement

In Supabase Dashboard, open **Authentication → Sign In / Providers → Email** and set **Email OTP length** to `6`, then save. After that, change the frontend constant back to six and test with a newly generated email. Old tokens are not converted when the setting changes.

This setting is outside the GitHub repository and is not changed by a Vercel deployment.

## Confirmation-email verification procedure

After saving the confirmation template, use a brand-new email address that has never existed in Supabase Auth. Confirm that the template contains visible `{{ .Token }}` text and contains neither `{{ .ConfirmationURL }}` nor an anchor whose `href` is `{{ .Token }}`.

Then verify the following sequence:

1. A new signup reaches the OTP screen.
2. The confirmation email is recorded by Brevo.
3. The message appears in the recipient inbox or spam folder.
4. The token length matches the configured Email OTP length.
5. A wrong token produces an invalid-code message.
6. An expired token produces an expired-code message.
7. A correct token creates the session and routes the user into onboarding.

If Brevo records the confirmation message but Gmail receives nothing, export the Brevo event detail for that exact message. The useful statuses are delivered, deferred, soft bounce, hard bounce, blocked, or rejected. A generic “sent” record is not enough to prove inbox delivery.

## Current status

- **OTP frontend mismatch:** fixed for the currently observed eight-digit production setting.
- **Reset email format:** corrected and visibly contains an eight-digit code.
- **Invalid versus expired UI feedback:** fixed where Supabase supplies an expiry-specific error code.
- **Confirmation email inbox delivery:** not proven by the available logs; Brevo acceptance and Gmail inbox placement remain separate checks.
- **Six-digit product requirement:** not applied to the external Supabase setting because the available Supabase management interface does not expose Auth provider configuration changes. The dashboard setting must be changed manually if six digits are required.

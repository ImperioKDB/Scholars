# Scholars Frontend Audit Report

**Repository:** `/home/ubuntu/Scholars`  
**Review mode:** Static source audit; application source was not modified.  
**Prioritization:** Severity first, then user impact and leverage. **BLOCKER** means release-blocking; **HIGH** is a core-flow, accessibility, or broad mobile failure; **MEDIUM** is meaningful friction or a systemic quality gap; **LOW** is contained polish or recoverable friction.

## Executive summary

The frontend has a credible foundation: server-rendered route shells, a real student mobile drawer and bottom navigation, safe-area spacing, 44px native form controls, visible focus, live status messaging, reduced-motion coverage for several custom animations, responsive result cards, and useful loading/empty/retry states. The audit also found thoughtful comments and several prior hardening fixes; those were treated as intentional unless the implementation contradicted them.

No **BLOCKER** was found in static review. The highest-leverage problems are:

1. **Auth intent is lost:** protected deep links and apparently public landing catalogue links eventually send users to `/dashboard` instead of the requested destination.
2. **Onboarding is fragile on small screens and failed writes:** step 0's two primary actions are not mobile-safe, while “Skip for now” clears the local draft and navigates after a failed save.
3. **Accessible interaction contracts are broken in reusable components:** `FormField` cannot reliably label composite `Combobox` controls, the combobox does not expose active options to assistive technology, the closed mobile drawer remains focusable, and `ConfirmDialog` is unnamed and does not restore focus.
4. **Reduced-motion support is incomplete:** global/imperative smooth scrolling, confetti, drawer transitions, and Tailwind spinners can still animate for users who requested reduced motion.
5. **The product system drifts across routes:** mobile section state, catalogue filters, container widths, typography, and card surfaces are not consistently expressed.

The exact visual wrapping, touch hit testing, frame rate, hydration cost, contrast in rendered contexts, and screen-reader announcements still require a short live validation pass. Those uncertainties are explicitly marked below.

## Strengths worth preserving

- **Solid mobile shell:** student layouts reserve header and bottom-tab space (`app/dashboard/layout.tsx:15-18` and equivalent layouts); the student drawer has overlay/focus handling, 44px controls, a 56px bottom bar, and safe-area padding (`components/Sidebar.tsx:205-277`).
- **Good baseline accessibility:** global `:focus-visible`, 44px native inputs/selects/textareas, and 16px mobile form text (`app/globals.css:22-43`); `FormField` correctly labels native direct children and connects error ids in the common case (`components/FormField.tsx:16-39`).
- **Useful state communication:** `StatusMessage` uses alert/status roles, and async controls commonly expose `aria-busy`; route loading files mirror the actual page structure rather than showing only a generic spinner.
- **Responsive content patterns:** scholarship and opportunity cards use one-column mobile layouts, `min-w-0`, and wrapped metadata (`components/ScholarshipCard.tsx:95-152`, `components/OpportunityCard.tsx:113-130`).
- **Good interaction details:** save state uses `aria-pressed`, contextual labels, disabled pending state, and 44px targets (`components/ScholarshipCard.tsx:40-62`); the student shell has a skip link and section-aware drawer matching (`components/Sidebar.tsx:190-205`).
- **Motion safeguards already present:** several custom animations and skeleton shimmer are gated under reduced motion (`app/globals.css:194-227`); custom motion generally uses transform/opacity, and public carousels use user-driven scroll snap rather than autoplay.
- **Recovery affordances:** main catalogue lists have retry/empty states; applications supports status updates, retry messaging, confirmation before stopping tracking, and records provider-link clicks without claiming a provider submission.
- **Intentional choices not counted as defects:** the `font-mono` mapping to Manrope is explicitly documented as a deliberate data-label emphasis token (`tailwind.config.ts:38-47`), so it is not reported as an accidental regression. The contained admin table overflow is also a deliberate prior fix, not uncontrolled document overflow.

### Hypotheses requiring live/device validation

The table marks these explicitly as hypotheses: **#28 shimmer paint**, **#29 repeated blur compositing**, and **#30 hydration breadth**. They are structurally plausible and worth profiling, but static inspection cannot establish frame drops, battery cost, or route timing. The onboarding width issue (#2) is a confirmed layout risk from deterministic sizing, but exact clipping and browser flex behavior still need 320px/375px rendering. The contrast calculation for placeholder text should likewise be checked against any component-specific background overrides.

## Quick wins (high leverage, low coordination)

1. Fix auth return paths in login, Google, signup, and callback tests.
2. Stack onboarding step-0 actions at the smallest breakpoint.
3. Stop clearing onboarding drafts or navigating after failed skip saves; add a visible retry.
4. Forward composite-field naming props and repair the combobox listbox/active-option contract.
5. Unmount or inert the closed student drawer; restore focus on close.
6. Add a labelled confirmation dialog and focus restoration.
7. Add reduced-motion fallbacks for smooth scrolling, `animate-spin`, confetti, and drawer transforms.
8. Add ids/labels to report and draft controls, `aria-current` to the step indicator, and radio semantics to binary choices.
9. Read `discipline` from the rejection URL and expose saved-query errors.
10. Keep mobile Log in visible and add a section-aware mobile-tab active state.

## Deeper fixes

- **Create shared interaction primitives:** one accessible combobox, dialog, disclosure/popover, form-field contract, and mobile navigation primitive should replace route-local variants.
- **Make data writes transactional from the user’s perspective:** preserve local drafts, distinguish request failure from empty data, and require acknowledgement before destructive navigation.
- **Define a product surface system:** named container widths, catalogue filters, result cards, empty states, radii, shadows, button hierarchy, icon family, and type roles should be shared tokens/components rather than route-level class recipes.
- **Narrow client boundaries:** keep static cards and route sections in Server Components; isolate interactive save/share/feedback leaves and measure route JS/hydration in a production build.
- **Run an accessibility and device matrix:** keyboard-only traversal, VoiceOver/NVDA, 320/375/768px widths, iOS Safari and Android Chrome, `prefers-reduced-motion`, `prefers-reduced-transparency`, and slow-network failure paths.

## Audit scope and limitations

- Reviewed the supplied project guidance files and re-read the cited source locations for every retained finding.
- Reviewed responsive layout, accessibility/forms, motion/performance, core flows, and visual consistency. No application source files were modified; no packages were installed.
- This was a static source audit. No browser/device render, screen-reader session, contrast inspector, production build, bundle analyzer, Supabase data/policy test, or Chrome performance trace was run.
- “Confirmed” means the cited code violates a stated contract or creates a deterministic source-level defect. Runtime severity may still vary with viewport, content, browser, device, backend response, or assistive technology.
- “Hypothesis” means the code pattern warrants profiling but static evidence cannot prove user-visible jank or timing cost.
- No blocker was found. The student shell, focus baseline, native form sizing, loading/empty/retry states, card responsiveness, and several reduced-motion rules are already sound; remediation should extend those patterns rather than replace the product wholesale.
